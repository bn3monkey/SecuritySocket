2. Server Multiplex Architecture

서버는 단일 thread + multiplex event loop로 동작. SocketMultiEventListener (poll/epoll wrapper) 하나가 listening socket과 모든 client fd를 감시. 각 fd의 READ/WRITE/DISCONNECT 이벤트를 받아 해당 ClientConnectionImpl로 dispatch. Connection은 non-blocking — 한 번 호출에 받을 수 있는 만큼만 처리하고 즉시 반환. Connection의 새 state에 따라 listener의 이벤트 타입 (READ ↔ WRITE) 변경.

2-4. Server pseudocode

void RequestServer::run(RequestHandler* handler) {
    SocketMultiEventListener listener;
    listener.open();
    listener.addEvent(_listening_socket, ACCEPT);

    while (_is_running) {
        auto events = listener.wait(timeout);

        for (auto& event : events) {
            switch (event.type) {
            case ACCEPT: {
                auto socket = _listening_socket->accept();
                auto* conn = _connection_pool.acquire(socket, handler);
                listener.addEvent(conn, READ);
                handler->onConnected(*conn);   // state = Sniffing
                break;
            }
            case READ: {
                auto* conn = static_cast<ClientConnectionImpl*>(event.context);
                conn->handleRead();
                adjustListener(listener, conn);   // state 기반 READ/WRITE/none
                break;
            }
            case WRITE: {
                auto* conn = static_cast<ClientConnectionImpl*>(event.context);
                conn->handleWrite();
                adjustListener(listener, conn);
                break;
            }
            case DISCONNECTED: {
                auto* conn = static_cast<ClientConnectionImpl*>(event.context);
                handler->onDisconnected(*conn);
                listener.removeEvent(conn);
                _connection_pool.release(conn);
                break;
            }
            }
        }

        // ※ SLOW worker 완료 통지는 별도 처리 불필요.
        //   Worker가 직접 listener.addEvent(socket, WRITE) 호출 → listener 내부 wakeup으로
        //   wait()가 즉시 깨어남 → 다음 iteration에서 WRITE 이벤트로 자연스레 처리.
    }

    listener.close();
}

// state에 따라 listener event type 변경
void adjustListener(SocketMultiEventListener& listener, ClientConnectionImpl* conn) {
    auto desired = listenerEventFor(conn->state());   // 위 §2-3 매핑표
    if (desired != conn->currentListenerEvent()) {
        listener.modifyEvent(conn, desired);
        conn->setCurrentListenerEvent(desired);
    }
}

2-5. FAST vs SLOW Dispatch

전제: SocketMultiEventListener는 cross-thread에서 안전. addEvent/modifyEvent/removeEvent 호출 시 내부 wakeup으로 wait() 중인 thread를 즉시 깨움 (Linux: eventfd / Windows: loopback socket pair, listener 당 1개).

Mode실행 threadEvent loop 영향완료 통지
FAST Event loop thread (handleRead 안에서 sync) handler 실행 동안 다른 fd 처리 차단 handleRead 반환 즉시 SendingResponse 진입 + listener.modifyEvent(WRITE)
SLOW connection별 worker thread handleRead 즉시 반환. event loop 차단 없음 worker가 직접 listener.addEvent(socket, WRITE) 호출
→ listener 내부 wakeup → event loop 즉시 깨어남 → 다음 wait()에서 WRITE 이벤트 fire → 자연스레 case WRITE 처리
READ_STREAM / WRITE_STREAM worker handleRead 즉시 반환. event loop가 더 이상 이 fd 안 봄 stream 종료 시 worker가 connection 해제 또는 normal flow 복귀 signal

사용자의 classifyMode(header) 반환값에 따라 결정. FAST는 context switch 비용 절약, SLOW는 event loop blocking 방지.

※ Listener 내부 wakeup이 cross-thread 호출을 즉시 반영하기 때문에 per-connection wakeup fd가 불필요. Worker는 그저 listener.addEvent 호출하면 됨 — 별도 signal 메커니즘 필요 없음.

3. Connection State Diagram (Event-Driven)

설계 원칙: 모든 state는 wait point — "다음에 어떤 외부 이벤트를 기다리고 있는가"를 표현. 외부 이벤트는 4종뿐: E_Accept / E_Read / E_Write / E_Disconnected. Handler 호출, 파싱 완료 같은 내부 milestone은 state 전이로 모델링하지 않음 — 한 E_Read/E_Write Action 안에서 sync 수행.

※ 외부 이벤트는 4종: socket의 POLLIN / POLLOUT / POLLHUP/ERR/NVAL, listening fd의 새 연결. SLOW worker 완료는 별도 이벤트가 아니라 worker가 직접 listener.addEvent(socket, WRITE) 호출 → listener 내부 wakeup으로 자연스레 다음 E_Write 이벤트로 들어옴. 내부 milestone (파싱 완료, handler 반환 등)은 Action 내부에서 sync 처리되고 state 전이로 모델링하지 않음.

Protocol grouping: Sniffing은 연결 시작 직후 최대 1회만 진입. 이후 connection은 sniff 결과 (HTTP / Custom) 또는 HTTP Upgrade 결과 (WebSocket) 에 따라 하나의 protocol identity 를 가지며, 같은 그룹의 state 끼리만 순환:

  • HTTP 그룹: ReceivingHttpRequest → SendingHttpResponse → WaitingForNextHttpRequest → ... (keep-alive)
  • WebSocket 그룹: SendingHandshakeResponse → WaitingForNextWebSocketMessage → ReceivingWebSocketFrame → SendingWebSocketResponse → ...
  • Custom 그룹: ReceivingCustomMessage → SendingCustomResponse → WaitingForNextCustomMessage → ...

Cross-protocol transition 없음 (예: Custom 메시지 후 HTTP 요청, WebSocket → HTTP 등). 진입 경로: HTTP / Custom 은 byte 0 sniff, WebSocket 은 HTTP Upgrade 핸드셰이크 (RFC 6455). Mid-connection protocol switch 지원 안 함.

5. Action 정의

각 (Event, From) 조합은 하나의 Action 함수로 표현. 함수는 내부 분기에 따라 ActionResult enum을 반환하고, transition table이 이 코드로부터 다음 state를 결정. 

// State machine 골격
ConnectionState transition(ConnectionState current, Event event) {
    auto result = action(current, event);   // 각 action은 ActionResult enum 반환
    return mapResultToNextState(current, event, result);
}

5-3. Listener의 cross-thread 안전성 — SLOW dispatch 기반

전제: SocketMultiEventListener의 addEvent/modifyEvent/removeEvent/wait는 모두 cross-thread 안전. 이들 함수는 내부 lock으로 자료 구조를 보호하고, 추가로 내부 wakeup fd를 가지고 있어 modification 시 wait 중인 thread를 즉시 깨움 (Linux: eventfd, Windows: loopback socket pair, listener 당 1개).

따라서 SLOW dispatch는 다음과 같이 단순하게 처리됨: 

// Main thread (handleHttpRequest 내부, SLOW 분기)
listener.removeEvent(_socket);    // socket을 listener에서 제거
queueToWorker(task);               // worker로 dispatch
return ROUTE_DISPATCHED_SLOW;      // state machine: state = SendingHttpResponse

// Worker thread
void workerExecute() {
    handler->process(*conn, req, resp);
    serializeHttpResponse();                                // _output_buffer 채움
    listener.addEvent(_conn, SocketEventType::WRITE);       // ★ 직접 추가 → 내부 wakeup으로 main thread 깨움
}

// Main thread (다음 wait()에서)
case WRITE:
    handleHttpResponseWrite();    // _output_buffer 송신

왜 이 방식이 안전한가:

  • SLOW 진입 race 방지: Action 함수에서 queueToWorker보다 먼저 listener.removeEvent(socket) 호출. socket이 listener에서 빠진 후에 worker schedule되므로, worker가 즉시 실행되어도 peer의 추가 byte로 인한 socket POLLIN 처리가 안 일어남 → buffer race 없음.
  • Worker 완료 wake: Worker가 listener.addEvent 호출 시, listener 내부의 wakeup fd가 자동 signal → 이미 wait 중인 main thread가 즉시 깨어남 → 다음 wait()에서 새 fd (socket WRITE)가 result에 포함되어 정상 dispatch.
  • Per-connection wakeup fd 불필요: Listener 내부 wakeup이 모든 cross-thread 신호를 처리. SocketUserEvent 같은 별도 클래스 없이도 worker 완료 통지가 작동.

따라서 모든 Action 함수는 listener를 인자로 받음 (SLOW 진입 시 removeEvent 호출하기 위함): 

// state machine 골격 — listener 인자 전달
ConnectionState transition(ClientConnectionImpl& conn,
                           SocketMultiEventListener& listener,
                           Event event) {
    auto result = conn.action(listener, event);     // listener를 함께 전달
    return mapResultToNextState(conn, listener, event, result);
}

Worker thread도 connection이 소유한 listener 참조를 통해 같은 listener에 접근.

SniffResult handleSniff() {
    int n = recv(_input_buffer.data() + _input_received,
                 _input_buffer.size() - _input_received);
    if (n <= 0) return SniffResult::FAILED;
    _input_received += n;

    switch (ProtocolSniffer::detect(_input_buffer.data(), _input_received)) {
        case Protocol::HTTP:      return SniffResult::DETECTED_HTTP;
        case Protocol::CUSTOM:    return SniffResult::DETECTED_CUSTOM;
        case Protocol::NEED_MORE: return SniffResult::NEED_MORE;
        default:                  return SniffResult::FAILED;
    }
}

enum class HttpRequestResult {
    NEED_MORE_BYTES,
    UPGRADE_REQUESTED,
    ROUTE_DISPATCHED_FAST,
    ROUTE_DISPATCHED_SLOW,
    ERROR_MALFORMED,
    ERROR_BODY_TOO_LARGE,
    ERROR_ROUTE_NOT_FOUND,
    SOCKET_ERROR
};

HttpRequestResult handleHttpRequest(SocketMultiEventListener& listener) {
    // 1. byte 수신
    int n = recv(_input_buffer.data() + _input_received, ...);
    if (n <= 0) return HttpRequestResult::SOCKET_ERROR;
    _input_received += n;

    // 2. header 파싱 (picohttpparser, incremental)
    auto parse = parseHttpHeader(_input_buffer, _input_received, &_header_index);
    if (parse == ParseState::INCOMPLETE) return HttpRequestResult::NEED_MORE_BYTES;
    if (parse == ParseState::MALFORMED) {
        serializeHttpResponse(400, "Bad Request");
        return HttpRequestResult::ERROR_MALFORMED;
    }
    _header_end = _header_index.endOffset();

    // 3. body 크기 검증
    size_t content_length = _header_index.contentLength();
    if (content_length > _config.max_http_request_body_size) {
        serializeHttpResponse(413, "Payload Too Large");
        return HttpRequestResult::ERROR_BODY_TOO_LARGE;
    }

    // 4. body 누적 미완료 시 다시 받기
    size_t body_received = _input_received - _header_end;
    if (body_received < content_length) {
        return HttpRequestResult::NEED_MORE_BYTES;
    }
    _body_start = _header_end;
    _body_end   = _header_end + content_length;

    // 5. WebSocket Upgrade 검출
    if (_header_index.hasUpgrade("websocket")) {
        if (!_ws_config.valid() || !matchesPattern(path(), _ws_config.pattern)) {
            serializeHttpResponse(404, "Not Found");
            return HttpRequestResult::ERROR_ROUTE_NOT_FOUND;
        }
        computeWsAccept(_header_index.secWebSocketKey());
        serializeHandshakeResponse();
        return HttpRequestResult::UPGRADE_REQUESTED;
    }

    // 6. HTTP 라우트 매칭
    auto* route = _router.match(method(), path());
    if (!route) {
        serializeHttpResponse(404, "Not Found");
        return HttpRequestResult::ERROR_ROUTE_NOT_FOUND;
    }
    fillPathParams(route);

    // 7. FAST / SLOW 분기
    if (route->mode == RequestProcessingMode::FAST) {
        auto req  = makeHttpRequest();
        auto resp = makeHttpResponse();
        route->handler(*this, req, resp);
        serializeHttpResponse();
        return HttpRequestResult::ROUTE_DISPATCHED_FAST;
    }
    // ★ SLOW: socket을 listener에서 빼고 queue
    //   worker가 완료 후 listener.addEvent(socket, WRITE) 직접 호출 → 내부 wakeup으로 main thread 깨움
    listener.removeEvent(_socket);
    queueToWorker(route, listener);    // worker는 listener 참조도 받음
    return HttpRequestResult::ROUTE_DISPATCHED_SLOW;
}

enum class WebSocketFrameResult {
    NEED_MORE_BYTES,                  // frame header 또는 payload 미완성
    FRAGMENT_RECEIVED,                // FIN=0, payload 누적 후 다음 frame 대기
    CONTROL_PING_HANDLED,             // PONG 자동 송신됨
    CONTROL_PONG_HANDLED,             // 통계만 갱신
    DISPATCHED_FAST,                  // Custom handler 호출 완료 + response 직렬화
    DISPATCHED_FAST_NO_RESPONSE,      // STREAM mode (processWithoutResponse)
    DISPATCHED_SLOW,                  // worker queue로 enqueue
    ERROR_CONTROL_CLOSE,              // Close echo 송신됨
    ERROR_TEXT_FRAME,                 // Close 1003 송신됨
    ERROR_INVALID_FRAME,              // Close 1002 송신됨
    SOCKET_ERROR
};

WebSocketFrameResult handleWebSocketFrame(SocketMultiEventListener& listener) {
    int n = recv(_input_buffer.data() + _input_received, ...);
    if (n <= 0) return WebSocketFrameResult::SOCKET_ERROR;
    _input_received += n;

    auto decode = decodeWebSocketFrame(_input_buffer, _input_received, &_frame_state);
    if (decode == DecodeState::HEADER_INCOMPLETE ||
        decode == DecodeState::PAYLOAD_INCOMPLETE) {
        return WebSocketFrameResult::NEED_MORE_BYTES;
    }
    if (decode == DecodeState::INVALID) {
        encodeCloseFrame(1002, _output_buffer);    // _output_buffer에 Close frame 채움
        return WebSocketFrameResult::ERROR_INVALID_FRAME;
    }
    // frame 완성 + in-place unmask 완료

    // opcode별 처리 — 즉시 send 하지 않고 _output_buffer에 채움
    switch (_frame_state.opcode) {
        case WsOpcode::PING:
            // PONG frame을 _output_buffer에 채움 → SendingWebSocketResponse로 전이
            encodePongFrame(_frame_state.payload, _output_buffer);
            return WebSocketFrameResult::PONG_TO_SEND;
        case WsOpcode::PONG:
            // 수신한 PONG은 무시 (통계 갱신만)
            return WebSocketFrameResult::CONTROL_PONG_HANDLED;
        case WsOpcode::CLOSE:
            // Close echo를 _output_buffer에 채움 → Closing으로 전이
            encodeCloseEchoFrame(_frame_state.payload, _output_buffer);
            return WebSocketFrameResult::ERROR_CONTROL_CLOSE;
        case WsOpcode::TEXT:
            encodeCloseFrame(1003, _output_buffer);
            return WebSocketFrameResult::ERROR_TEXT_FRAME;
        case WsOpcode::BINARY:
        case WsOpcode::CONTINUATION:
            break;
        default:
            encodeCloseFrame(1002, _output_buffer);
            return WebSocketFrameResult::ERROR_INVALID_FRAME;
    }

    // FIN=0 fragmented → payload 누적 유지, 다음 frame 대기
    if (!_frame_state.fin) {
        return WebSocketFrameResult::FRAGMENT_RECEIVED;
    }

    // 메시지 완성 — Custom 프로토콜 size 검증
    size_t msg_size = _input_received - _input_consumed;
    size_t hs = _custom_handler->headerSize();
    const void* header = _input_buffer.data() + _input_consumed;
    size_t ps = (msg_size >= hs) ? _custom_handler->payloadSize(header) : 0;
    if (msg_size != hs + ps) {
        encodeCloseFrame(1002, _output_buffer);
        return WebSocketFrameResult::ERROR_INVALID_FRAME;
    }
    _header_end  = _input_consumed + hs;
    _payload_end = _header_end + ps;

    // Custom handler dispatch
    auto mode = _custom_handler->classifyMode(header);
    if (mode == RequestProcessingMode::FAST) {
        auto req  = makeCustomProtocolRequest();
        auto resp = makeCustomProtocolResponse();
        _custom_handler->process(*this, req, resp);
        encodeWebSocketFrame(resp.data(), resp.length(), /*binary=*/true);
        return WebSocketFrameResult::DISPATCHED_FAST;
    }
    if (mode == RequestProcessingMode::READ_STREAM ||
        mode == RequestProcessingMode::WRITE_STREAM) {
        auto req = makeCustomProtocolRequest();
        _custom_handler->processWithoutResponse(*this, req);
        return WebSocketFrameResult::DISPATCHED_FAST_NO_RESPONSE;
    }
    // ★ SLOW: socket을 listener에서 빼고 queue
    //   worker가 완료 후 listener.addEvent(socket, WRITE) 직접 호출 → 내부 wakeup으로 main thread 깨움
    listener.removeEvent(_socket);
    queueToWorker(_custom_handler, listener);   // state로 protocol 식별, 별도 context 불필요
    return WebSocketFrameResult::DISPATCHED_SLOW;
}

CustomMessageResult handleCustomMessage(SocketMultiEventListener& listener) {
    int n = recv(_input_buffer.data() + _input_received, ...);
    if (n <= 0) return CustomMessageResult::SOCKET_ERROR;
    _input_received += n;

    size_t accumulated = _input_received - _input_consumed;

    if (_input_received < _payload_end) {
        return CustomMessageResult::NEED_MORE_BYTES;

    if (mode == RequestProcessingMode::FAST) {
        auto req  = makeCustomProtocolRequest();
        auto resp = makeCustomProtocolResponse();
        _custom_handler->process(*this, req, resp);
        return CustomMessageResult::DISPATCHED_FAST;

    if (mode == RequestProcessingMode::READ_STREAM ||
        mode == RequestProcessingMode::WRITE_STREAM) {
        auto req = makeCustomProtocolRequest();
        _custom_handler->processWithoutResponse(*this, req);
        return CustomMessageResult::DISPATCHED_FAST_NO_RESPONSE;

    //   worker가 완료 후 listener.addEvent(socket, WRITE) 직접 호출 → 내부 wakeup으로 main thread 깨움

6-5. SLOW Dispatch — Worker thread 동작

핵심 원칙: Worker thread는 handler 실행 + output_buffer 채움 후, 직접 listener.addEvent(socket, WRITE) 호출. Listener 내부 wakeup이 main thread의 wait()를 즉시 깨움 → 다음 wait()에서 socket POLLOUT 받음 → 자연스레 case WRITE 처리.

→ 별도 E_WorkerCompleted event 없음. AwaitingWorkerCompletion state 없음. handleWorkerCompletion action 없음. Worker가 완료한 후의 흐름은 일반 SendingXxxResponse + E_Write 처리와 완전히 동일.

Worker 동작 — 흐름 요약

// Connection 당 worker thread 1개, lazy 생성. Task slot은 1개 (queue 아님).
// 상세 구현 코드는 §7-4 참조.

void ClientConnectionImpl::workerLoop() {
    while (!_worker_should_stop) {
        // 1. task slot에서 꺼냄 (없으면 cv로 대기)
        auto task = waitAndTakeTask();

        // 2. handler 실행 (가장 무거운 부분, ms 단위 가능)
        task.handler_call();

        // 3. output_buffer에 응답 직렬화 — state()로 분기
        switch (state()) {
            case SendingHttpResponse:      serializeHttpResponse(); break;
            case SendingWebSocketResponse: encodeWebSocketFrame(...); break;
            case SendingCustomResponse:    /* raw, no serialize */ break;
        }

        // 4. socket을 listener에 재등록
        //    response 있으면 WRITE, 없으면 READ (다음 메시지 대기)
        if (_no_response) {
            task.listener.addEvent(this, SocketEventType::READ);
        } else {
            task.listener.addEvent(this, SocketEventType::WRITE);
        }
        // ★ listener 내부 wakeup으로 main thread wait() 즉시 깨어남
    }
}

※ Worker thread는 connection 당 1개, lazy 생성. 첫 SLOW dispatch 시 생성, 이후 connection lifetime 동안 유지. FAST만 쓰는 connection은 worker thread 없음 (자원 절약).

※ WorkerContext field 불필요: connection의 state()만으로 protocol 식별 가능. 한 connection이 동시에 둘 이상 요청을 처리하지 않으므로 state가 곧 컨텍스트 — task slot도 1개로 충분.

Edge case — Worker 실행 중 peer 끊김

  • Socket이 listener에 없으니 main thread는 peer 끊김을 모름
  • Worker는 그대로 끝까지 실행 → output_buffer 채움 → listener.addEvent(socket, WRITE)
  • 다음 wait()에서 socket POLLOUT + POLLHUP 같이 옴 (peer 끊김으로 POLLHUP)
  • Dispatcher: POLLHUP 우선 → handleDisconnect → cleanup
  • 또는 send 시도 → SOCKET_ERROR → Closed
  • → 정상 처리, 동기화 메커니즘으로 안전

7-4. ClientConnectionImpl — Action 시그니처 + Worker 멤버

Worker는 connection 당 1개, lazy 생성. Connection이 평생 FAST만 쓰면 worker thread 생성 안 됨. 첫 SLOW dispatch 시점에 worker thread 시작, 이후 connection lifetime 동안 유지.

Task slot은 1개: 한 connection은 동시에 한 요청만 처리하므로 queue 불필요. 단일 멤버 변수로 충분. C++14 호환 위해 std::optional 대신 listener == nullptr 이 empty 지표. 

class ClientConnectionImpl : public ClientConnection {
public:
    // ── Action 시그니처 ──
    // SLOW 진입 시 listener.removeEvent 호출 위해 listener 인자 받음
    HttpRequestResult     handleHttpRequest    (SocketMultiEventListener& listener);
    WebSocketFrameResult  handleWebSocketFrame (SocketMultiEventListener& listener);
    CustomMessageResult   handleCustomMessage  (SocketMultiEventListener& listener);
    // 나머지 handle* 함수도 일관성을 위해 listener 인자 받음

private:
    // ── Worker (lazy 생성) ──
    std::thread                   _worker_thread;          // 처음엔 비활성
    bool                          _worker_should_stop = false;

    // ── Task slot — queue 아님, 단일 ──
    //   listener 는 pointer (C++14 std::optional 미사용)
    //   listener == nullptr ↔ slot empty
    struct WorkerTask {
        SocketMultiEventListener* listener = nullptr;      // nullptr → empty
        std::function<void()>     handler_call;            // FAST 분기와 동일한 dispatch
    };
    WorkerTask                    _pending_task;           // ★ 한 slot, default = empty
    std::mutex                    _task_mtx;
    std::condition_variable       _task_cv;
};

void ClientConnectionImpl::queueToWorker(
        std::function<void()> handler_call,
        SocketMultiEventListener& listener)
{
    // ★ 첫 SLOW 시점에 worker thread 시작
    if (!_worker_thread.joinable()) {
        _worker_thread = std::thread(&ClientConnectionImpl::workerLoop, this);
    }

    {
        std::lock_guard<std::mutex> lock(_task_mtx);
        _pending_task.listener     = &listener;
        _pending_task.handler_call = std::move(handler_call);
    }
    _task_cv.notify_one();
}

Worker loop

void ClientConnectionImpl::workerLoop() {
    while (true) {
        SocketMultiEventListener* listener_ptr = nullptr;
        std::function<void()>     handler_call;
        {
            std::unique_lock<std::mutex> lock(_task_mtx);
            _task_cv.wait(lock, [&] {
                return _pending_task.listener != nullptr || _worker_should_stop;
            });
            if (_worker_should_stop) return;

            listener_ptr              = _pending_task.listener;
            handler_call              = std::move(_pending_task.handler_call);
            _pending_task.listener    = nullptr;   // slot 비움
        }
        auto& listener = *listener_ptr;

        // 1. handler 실행 (가장 무거운 부분, ms 단위 가능)
        handler_call();

        // 2. output_buffer에 응답 직렬화 — state로 분기
        switch (state()) {
            case ConnectionState::SendingHttpResponse:
                serializeHttpResponse();
                break;
            case ConnectionState::SendingWebSocketResponse:
                encodeWebSocketFrame(_output_buffer.data(), _output_buffer.size(),
                                     /*binary=*/true);
                break;
            case ConnectionState::SendingCustomResponse:
                // raw Custom은 _output_buffer 그대로 (serialize 불필요)
                break;
            default:
                break;
        }

        // 3. socket을 listener에 재등록 (response 유무에 따라 READ/WRITE)
        if (_no_response) {
            listener.addEvent(this, SocketEventType::READ);
        } else {
            listener.addEvent(this, SocketEventType::WRITE);
        }
        // ★ listener 내부 wakeup으로 main thread wait() 즉시 깨어남
    }
}

Connection 종료 시 worker 정리

ClientConnectionImpl::~ClientConnectionImpl() {
    if (_worker_thread.joinable()) {
        {
            std::lock_guard<std::mutex> lock(_task_mtx);
            _worker_should_stop = true;
        }
        _task_cv.notify_one();
        _worker_thread.join();
    }
}

요약:

  • Worker thread는 connection 당 1개, lazy 생성
  • FAST만 쓰는 connection은 worker thread 생성 안 됨 → 자원 절약
  • Task slot은 단일 WorkerTask 멤버 — queue 불필요 (동시 처리할 task 없음). C++14 호환 위해 std::optional 대신 listener == nullptr 이 empty 지표
  • WorkerContext field 없음 — connection.state()로 protocol 식별
  • Per-connection wakeup fd 없음 — listener 내부 wakeup으로 충분

8. 불변 조건 (Invariants)

  • 한 fd당 한 ConnectionState. ClientConnectionImpl 멤버로 유지.
  • 모든 state는 wait point. handler 호출 / 파싱 / unmask 같은 sync 작업은 Action 내부에서 처리되고 별도 state로 모델링하지 않음.
  • Protocol identity는 연결 lifetime 동안 불변. Sniffing은 최대 1회 진입 (연결 시작 직후). HTTP / Custom 으로 한 번 정해지면 같은 그룹 state 끼리만 순환. Mid-connection protocol switch (예: Custom 메시지 후 HTTP, WebSocket → HTTP) 지원 안 함 — 잘못된 byte는 parse error → Closing.
  • Closed는 terminal — 다른 상태로 전이 안 됨.
  • WebSocket 흐름은 항상 HTTP를 거쳐 진입 (Upgrade handshake, RFC 6455). raw bytes로 직접 WS state 진입 불가. Upgrade 성공 후에는 HTTP state 로 복귀 안 함.
  • FIN=0 fragmented frame 수신 시 ReceivingWebSocketFrame에서 self loop. payload 누적은 유지 (다음 frame과 이어붙임).
  • 모든 WaitingForNext* state는 A_ResetMessageOffsets 이후 진입 — buffer offset이 정리된 상태.
  • SLOW dispatch 중에는 socket이 listener에서 일시 제거됨. main thread는 이 connection의 E_Read/E_Write 안 받음. Worker가 listener.addEvent(socket, WRITE) 호출 시점에 다시 listener에 들어가고 다음 wait()에서 E_Write 발생.
  • 모든 client state에서 E_Disconnected는 Closed로 직행. Closing 거치지 않음 (peer가 이미 끊었으므로 송신할 게 없음).
  • FAST와 SLOW의 차이는 E_Read Action 안에서 sync vs async 처리일 뿐. State 전이는 동일한 패턴 (모두 SendingXxxResponse로 감).
  • SLOW dispatch 순서 invariant: Action 함수 안에서 listener.removeEvent(socket)이 queueToWorker보다 반드시 먼저 호출되어야 함. 그렇지 않으면 worker가 즉시 실행되고 동시에 peer가 byte를 보낼 때 buffer race 발생.
  • Listener는 cross-thread 안전: addEvent/modifyEvent/removeEvent 모두 lock + 내부 wakeup으로 wait 중인 thread를 즉시 깨움. Worker가 직접 호출 가능.
  • Wakeup fd는 listener 당 1개: open()에서 생성, close()에서 정리. 매 SLOW dispatch마다 새로 만들지 않음.
  • Worker thread는 connection 당 1개, lazy 생성: 첫 SLOW dispatch 시점에 시작. FAST만 쓰는 connection은 worker 생성 안 됨 (자원 절약).
  • Task slot은 1개 (단일 WorkerTask 멤버, listener == nullptr 이 empty 지표 — C++14 호환): 한 connection이 동시에 둘 이상 요청을 처리하지 않으므로 queue 불필요. 다음 SLOW가 들어올 때는 이미 직전 task가 끝났음이 보장됨 (state가 Sending* → Waiting* → Receiving*을 거쳤어야 함).

9. 누락된 상태 / 향후 확장

  • Server-initiated WebSocket Close: 현재는 peer가 먼저 Close frame 보내는 경우만 처리. 서버가 Close 시작하는 경로는 A_SendCloseCode + Closing으로 통합 가능.
  • HTTP 100 Continue: Expect: 100-continue 헤더 처리 out of scope.
  • SSE (Server-Sent Events): 추가 시 StreamingHttpResponse state 필요 (response가 keep-open되어 계속 chunk 송신).
  • Idle timeout: WaitingForNext* state에서 일정 시간 무응답 시 강제 Close. 별도 timer event로 처리 (event loop의 wait timeout 활용).
  • Partial worker cancellation: SLOW dispatch 중 peer disconnect 시 worker thread 작업을 어떻게 cancel할지. 현재는 worker가 끝까지 실행하고 결과를 폐기.
  • Windows IOCP backend (v4 후속 마일스톤): 현재 WSAPoll 기반 reactor 모델이라 Windows에서 ~5000 동시 연결까지가 실용적 상한. 더 큰 규모면 IOCP proactor 모델 필요. State machine을 별도로 설계해야 함 (E_*Completed 기반). Reactor backend와 별도 코드 path로 공존 (libuv / Boost.Asio 패턴).
  • Linux epoll 업그레이드 (v3.x 또는 v4): poll → epoll 전환. 같은 reactor라 state machine 그대로. 10K 이상 idle 연결에서 wait 비용 O(N) → O(M) 개선. epoll은 kernel-level thread-safe라 wakeup 메커니즘도 불필요.

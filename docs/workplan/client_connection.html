2. 문제 정의

WIP ClientConnectionImpl 은 sniff·HTTP·WebSocket·Custom 의 recv/parse/dispatch/serialize 를 한 클래스의 13-state switch 로 처리한다. 결과:

  • 한 파일이 4개 프로토콜의 책임을 동시에 짊어져 비대해짐.
  • 프로토콜별 로직 경계가 흐려져 읽기/테스트가 어려움.
  • (사용자 지적) 합의 없이 Outcome 같은 통합 enum 이 끼어들어 명세(state-machine.html)와 어긋남.

3. 설계 원칙

  1. 한 connection = 한 protocol identity (state-machine.html §3, §8). Sniff 는 최대 1회. 이후 그룹 고정.
  2. 프로토콜별 Phase 클래스로 분해. 각 Phase 가 자기 그룹의 state·action·result enum 만 책임진다.
  3. Host 가 공유 자원 소유. socket, 단일 input/output buffer, SLOW worker, listener 조작은 Host(+worker) 만.
  4. 명세 어휘 유지. ConnectionState(13) + Event(4) 가 유일한 host-level 공용 어휘. action별 result enum 은 state-machine.html §7-3 그대로. 통합 Outcome enum 없음.
  5. Custom dispatch 는 공유. raw Custom 과 WS-tunnelled Custom 은 동일한 CustomProtocolRequestHandler 를 호출 — 한 벌의 dispatch 헬퍼를 두 Phase 가 공유.

5. action별 Output(result enum) 유지 + transition

state-machine.html §7-3 의 result enum 을 그대로 쓴다. 각 Phase 가 자기 action 의 result 를 mapResultToNextState(result) 로 다음 ConnectionState 에 매핑한다(§6 transition table). 통합 enum 없음. 

// 각 Phase 내부 (예: HttpPhase) — 명세 그대로
enum class HttpRequestResult {
    NEED_MORE_BYTES, UPGRADE_REQUESTED,
    ROUTE_DISPATCHED_FAST, ROUTE_DISPATCHED_SLOW,
    ERROR_MALFORMED, ERROR_BODY_TOO_LARGE, ERROR_ROUTE_NOT_FOUND, SOCKET_ERROR
};

ConnectionState HttpPhase::onReadable(Host& h, Listener& lsn) {
    HttpRequestResult r = handleHttpRequest(h, lsn);   // recv+parse+dispatch
    return mapResultToNextState(r);                    // §6-2 표
}

listener 조작은 누가? SLOW 진입은 action 안에서 lsn.removeEvent → h.queueToWorker 순서가 반드시 지켜져야 하므로(state-machine.html §8 invariant), action 이 listener 를 받는다. READ↔WRITE 의 일반 전환은 Host 가 새 state 로부터 유도(§2-3 매핑)해서 처리 → action 은 state 만 바꾸면 됨. SLOW 인 경우만 "socket 이 이미 빠졌으니 Host 는 re-arm 하지 말 것"을 알아야 하는데, 이는 "SLOW 로 간 state(예: SendingHttpResponse) + worker 가 재등록 예정" 규약으로 표현한다 (§7 참조).

6. 상태 전이 — 그룹 내 vs 그룹 간

6-1. 4가지 시나리오

  1. Sniff → Http → (keep-alive) Http 그룹 순환
  2. Sniff → Custom → Custom 그룹 순환
  3. Sniff → Http → WebSocket(Custom) → WS 그룹 순환
  4. (핸들러가 단일 프로토콜만 지원하면 Sniff 생략하고 해당 그룹에서 바로 시작)

6-2. Host 의 Phase 교체 메커니즘

Host 는 ConnectionState 가 어느 그룹에 속하는지 안다. Phase action 이 다른 그룹의 state 를 반환하면 Host 가 해당 Phase 객체로 교체하고, buffer 에 남은 byte 가 있으면 새 Phase 에게 즉시 다시 read 를 돌린다 (sniff 가 본 byte 를 HTTP/Custom 이 이어서 파싱; keep-alive/pipelined 동일 메커니즘). 

// Host 의 read 드라이브 루프 (개념)
Disposition handleEvent(Event ev, Listener& lsn) {
    if (ev == E_Disconnected) return CLOSE;
    if (ev == E_Write) { _state = _phase->onWritable(*this, lsn); afterTransition(lsn); ... }
    else /* E_Read */  {
        if (recv() <= 0) return ...;            // Host 가 공유 buffer 로 recv
        for (;;) {
            ConnectionState next = _phase->onReadable(*this, lsn);
            swapPhaseIfGroupChanged(next);      // Sniff→Http 등
            _state = next;
            if (!shouldKeepDraining(next)) break;  // 남은 byte 있고 read state 면 계속
        }
        afterTransition(lsn);                   // §2-3 으로 READ/WRITE re-arm (SLOW 제외)
    }
}
※ recv 위치 결정 필요(§8): recv 를 Host 가 한 번 해서 buffer 를 채우고 Phase 는 buffer 만 보게 할지, 아니면 state-machine.html 처럼 각 action 안에서 recv 할지. Host 일괄 recv 가 분해와 더 잘 맞아 보임(Phase 가 socket 비의존).

7. SLOW worker & listener invariant (Host 소유)

  • Worker: connection 당 1개, lazy(첫 SLOW 때 생성), single task slot(listener==nullptr 이 empty 지표, C++14). state-machine.html §7-4 그대로.
  • SLOW 진입 순서 invariant: action 안에서 listener.removeEvent(socket) → host.queueToWorker(call, listener).
  • Worker 완료: call()(handler+serialize+consume) 후 listener.addEvent(socket, WRITE) → 내부 wakeup 으로 main 깨어남 → 다음 wait 에서 E_Write.
  • call 의 serialize 부분은 프로토콜별이므로 각 Phase 가 람다로 캡슐화해 Host 에 넘긴다 (Host 는 protocol-agnostic).

8-3. RequestHandler → derived 복원 방법 (기술 검토)

RequestHandler 는 supportHttp() / supportUserProtocol() bool 로 "어떤 derived 인지" 알 수 있다. 하지만 그걸 안 뒤 실제 HttpRequestHandler* 로 변환하는 게 문제:

  • mileston §2-4 대로 HttpRequestHandler·CustomProtocolRequestHandler 는 RequestHandler 를 virtual 상속한다 (둘 다 상속하는 사용자 핸들러의 diamond 방지).
  • virtual base → derived 로의 static_cast 는 표준상 ill-formed (컴파일 에러).
  • reinterpret_cast 는 컴파일되지만 잘못된 포인터. virtual base subobject 는 offset 이 비자명 → 비트 재해석 시 UB.
  • RTTI off → dynamic_cast 불가.

→ RTTI 없이 올바른 유일한 방법은 각 derived 가 자기 타입을 반환하는 virtual self-accessor. bool 함수의 "타입 반환 버전"이며 파생당 한 줄 override: 

class RequestHandler {
    // 기존 bool 들 유지...
    virtual HttpRequestHandler*           asHttpRequestHandler()           { return nullptr; }
    virtual CustomProtocolRequestHandler* asCustomProtocolRequestHandler() { return nullptr; }
};
class HttpRequestHandler : public virtual RequestHandler {
    HttpRequestHandler* asHttpRequestHandler() override { return this; }  // 한 줄
};
class CustomProtocolRequestHandler : public virtual RequestHandler {
    CustomProtocolRequestHandler* asCustomProtocolRequestHandler() override { return this; }  // 한 줄
};

D6 확정: self-accessor 방식 채택 (cast 류는 virtual inheritance 와 호환 불가).
